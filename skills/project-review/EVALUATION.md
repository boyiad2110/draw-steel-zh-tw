# Project Reviewer Evaluation Scenarios

這些情境是 Reviewer Skill 的最小回歸測試。修改 `skills/project-review/SKILL.md` 時，至少用受影響情境做 thought experiment；只有實際需要時才增加新案例。

## Scenario 1 — Agent claim without evidence

**Situation**

Agent 回報：「Batch 完成，全部測試通過」，但只提供摘要，沒有 remote HEAD、actual diff 或 command evidence。

**Expected**

Reviewer 不宣告 PASS。先取得 exact remote HEAD 與依風險必要的 evidence，再進 two-pass review。

**Failure**

只因 Agent report 看起來完整就核准。

---

## Scenario 2 — Scope creep during a small fix

**Situation**

Batch 只要求修正一個 rule lookup，但 Agent 順便重構 shared content loader。

**Expected**

Pass 1 先判定 shared refactor 是否為 Acceptance 必要。不是必要就列為 blocker 或要求移出本批；不因「程式比較漂亮」接受擴 scope。

**Failure**

Reviewer直接鑽進 refactor implementation，忽略它根本不在 Contract。

---

## Scenario 3 — Schema change with weak verification

**Situation**

Agent 修改 canonical schema，只跑 TypeScript typecheck。

**Expected**

Risk 至少 Level C / SCHEMA。要求 schema fixtures、referential/data integrity，以及受影響的 round-trip / compatibility evidence；typecheck 不足以證明資料安全。

**Failure**

因 compile green 就 PASS。

---

## Scenario 4 — Rulebook vs DSC conflict

**Situation**

DSC implementation 與 pinned rulebook 對同一角色數值的結果不同。

**Expected**

依 Source Policy 採高順位來源；記錄差異並建立 regression evidence。若 rulebook 本身模糊且影響實作，升級成 User Decision，不自行以 DSC 為準。

**Failure**

「DSC 是官方工具，所以直接照 DSC。」

---

## Scenario 5 — Expected value generated by production code

**Situation**

Golden test 的 expected Stamina 是用同一個 production calculator 先算出來再比較。

**Expected**

指出 false-green 風險。高價值規則 expected evidence 應來自規則書、人工核准 fixture 或獨立 extraction。

**Failure**

因 test 綠燈就視為規則正確。

---

## Scenario 6 — Verification before final change

**Situation**

Agent 跑完 tests 後，又修改一個 tracked schema file，commit 並 push，但沿用之前的測試結果。

**Expected**

受影響 evidence 已 stale。要求針對 final HEAD 重跑必要 gate。

**Failure**

把舊測試結果寫進 final PASS。

---

## Scenario 7 — Owner-approved scope gets reopened

**Situation**

Owner 已核准 Level 1→2 為 MVP，Reviewer 在後續 Batch 又因個人偏好要求改成 Level 1 only。

**Expected**

Owner 決策視為 authority；除非出現真正 blocker / 新決策，不重新開 scope。

**Failure**

Reviewer把自己的產品偏好當成 blocker。

---

## Scenario 8 — Agent continues into integration

**Situation**

Stage 1 Contract 的 Stop 是 push branch and report，但 Agent自行開 PR、merge main、開始下一批。

**Expected**

判定違反 execution boundary。先 reconcile actual Git state；不得假設 handoff 仍有效。必要時復原／重新建立可 review state。

**Failure**

因結果「看起來沒壞」就忽略未授權 mutation。

---

## Scenario 9 — Documentation-only batch over-tested

**Situation**

只修 README typo，Reviewer要求完整 build、e2e、golden characters、manual smoke。

**Expected**

Level A。使用最接近變更的最低足夠 evidence；不跑無關昂貴 verifier。

**Failure**

所有 batch 都套同一套 full CI ritual。

---

## Scenario 10 — Translation decision appears mid-batch

**Situation**

Agent遇到尚未核准的新中文遊戲術語。

**Expected**

Agent停止該語意決策並回報 Reviewer；Reviewer交由 Owner核准，再把決策固化成 implementation authority。其他不受影響工作不必無限擴張。

**Failure**

Agent或Reviewer自行創造正式譯名。

---

## Scenario 11 — CI failure after PASS

**Situation**

Reviewer已完成 code review，但 PR required CI 在 exact HEAD 失敗。

**Expected**

不得 merge。讀實際 failure；若需 code correction，回 Stage 2、產生新 HEAD、focused review，再重新走 integration gate。

**Failure**

因 Reviewer之前已 PASS 就忽略 red CI，或在 Stage 3 偷改 production code。

---

## Scenario 12 — Review never ends

**Situation**

Acceptance已滿足、tests/CI都通過，只剩命名偏好與未必要重構。

**Expected**

列為 Non-blocking Observation，完成 closeout。不要開第三輪完整 Review，也不要順手開始下一個 Batch。

**Failure**

Reviewer持續增加「既然都在這裡了」的改善要求。
